# Funnel Runtime — архитектура

Почему проект устроен именно так. Что он делает — в README репозитория.

## Структура

```
packages/shared/   движок воронки + типы HTTP API (TS-исходники, без сборки)
apps/server/       Fastify 5 + SQLite (better-sqlite3)
apps/web/          React 19 SPA: воронка (/) и админка (/admin)
scripts/           generate (трафик), publish (публикация/откат) — CLI поверх HTTP API
configs/           выданные конфиги v1, v3 (не редактируются)
configs/translations/  переводы контента воронки: <funnelId>.<lang>.json
```

**Почему монорепо с общим пакетом.** Видимость шагов, навигация, валидация, расчёт результата и whitelist событий должны работать одинаково в браузере, на сервере (перепроверка в `POST /result`), в генераторе и тестах. Одна реализация в `@funnel/shared` исключает расхождения «фронт показал одно, сервер посчитал другое», а общие типы API делают контракт клиент–сервер проверяемым компилятором. Пакет отдаётся исходниками: Vite и tsup бандлят его сами — нет отдельного шага сборки и рассинхрона `dist`. npm workspaces: три пакета, `npm ci`, без лишних инструментов.

## Сервер

```
src/config.ts      env → типизированный конфиг (zod), падает при старте со списком ошибок
src/app.ts         buildApp(opts) — чистая фабрика, не читает process.env
src/server.ts      точка входа: loadConfig → buildApp → listen + graceful shutdown
src/routes/        HTTP: разбор входа (zod) → вызов сервиса
src/services/      бизнес-логика и весь SQL
src/db.ts          соединение (WAL), миграции, кеш prepared statements
src/http/          единственный error handler, раздача SPA
src/lib/           ServiceError, время
```

- **Фабрика + entry отдельно** — стандарт Fastify: тесты поднимают изолированные приложения на `:memory:` через `app.inject`, без портов и глобального состояния; окружение читает только `server.ts`.
- **routes → services → db.** Маршрут не знает про SQL, сервис не знает про HTTP (бросает `ServiceError`, который один обработчик превращает в `{error, message}`; 5xx маскируются). Repository/ORM не нужен: десяток таблиц, лишний слой только мешал бы.
- **Graceful shutdown.** SIGTERM/SIGINT → `app.close()` (дождаться запросов, закрыть БД), жёсткий таймаут 10 с. Railway шлёт SIGTERM при каждом деплое.
- **Админ-доступ через scope Fastify.** Открытый scope — конфиги и аналитика (нет id сессий и ответов), защищённый (`onRequest: requireAdmin`) — все мутации и списки сессий/событий. Доступ решает место объявления маршрута, а не сравнение URL-строк, поэтому `/api/%61dmin` не обходит проверку, а новый маршрут нельзя «забыть» защитить. Токен сравнивается `timingSafeEqual` по SHA-256.

## Данные

- **SQLite** разрешён заданием и не требует сторонних сервисов; better-sqlite3 синхронный — транзакции простые, без пула.
- **Миграции — append-only массив SQL** с учётом в `schema_migrations`; старая база поднимается сама при старте (есть тест апгрейда). Вторая итерация схему не меняла: шаги, события и результаты — данные конфига, а не колонки.
- **Версии неизменяемы.** `funnel_versions` хранит конфиг как загружен + хэш канонического JSON (тот же номер с другим содержимым → 409). `active_versions` — только указатель. `version_activations` — append-only журнал, читается как стек: publish/activate кладут, rollback снимает → откат всегда идёт назад по истории и одновременно служит аудитом.
- **Сессия навсегда хранит версию и вариант.** Клиент получает конфиг, уже разрешённый для варианта, поэтому старые сессии доходят до конца на своей версии после публикации и отката. Вариант = детерминированный хэш `experimentId:sessionId` по весам (или override из query-параметра при создании).

## События

- `event_id` — первичный ключ, вставка `ON CONFLICT DO NOTHING` → повтор пачки после timeout безопасен без отдельного хранилища идемпотентности.
- Пачка — одна транзакция, но каждое событие валидируется отдельно; плохое уходит в `rejected_events` с причиной, остальные принимаются.
- Версия, вариант и UTM берутся из строки сессии, а не из тела события: клиент не подделает атрибуцию. Разрешённые имена событий и свойства — из конфига версии сессии (v1-сессия не может прислать событие из v3).
- Сырые ответы живут только в `sessions.answers_json` (нужны для продолжения сессии); в событиях — только whitelisted примитивы.
- `session_started` пишет сервер в транзакции создания сессии — «начавшие» не зависят от клиентского flush.

## Аналитика

```
services/analytics/stats.ts    z-тест, median, ratio — чистая математика
services/analytics/derive.ts   события сессии → факты (viewed / progressed / reachedResult)
services/analytics/index.ts    когорта по фильтрам → KPI, шаги, A/B, версии, кампании
```

Единица — уникальная сессия. Факты сессии выводятся из _множества_ её событий относительно _её_ последовательности шагов (версия + вариант), а не по времени — поэтому дубли, повторные просмотры, возвраты и события не по порядку не искажают метрики, а A и B с разным порядком шагов сравниваются по `step_id`. Доля шага считается от сессий, у которых этот шаг вообще был. A/B-тест — внутри одной версии и только по случайно назначенным сессиям (override исключается). Три модуля тестируются отдельно; SQL статический и параметризованный.

## Веб

```
src/funnel/   FunnelController (сессия, навигация, сохранение) + очередь событий + экраны по type
src/admin/    по фичам: versions/, analytics/, events/, sessions/; общие components/, lib/
src/lib/      типизированный API-клиент
```

- **Воронка = контроллер вне React + тонкие компоненты.** Жизненный цикл сессии, URL `?step=`, back/forward, восстановление после refresh (локальное зеркало + debounced `PUT /state`) и правила эмиссии событий — в обычном TS-классе: нет stale closures, StrictMode не задваивает события, логика тестируется в node без DOM. Компоненты только рендерят шаг по `type`; неизвестный тип — безопасный fallback (совместимость будущих конфигов).
- **Очередь событий** — клиентская половина идемпотентности: localStorage (переживает перезагрузку), удаление только после ответа сервера, повтор с backoff теми же `event_id`, `sendBeacon` при уходе со страницы.
- **Админка по фичам**, а не по типам файлов. Опрос через `usePolling` поверх чистого `createPoller` (AbortController на запрос, один таймер, пауза на скрытой вкладке) — для четырёх эндпоинтов отдельная data-fetching библиотека избыточна.
- **Разделение бандлов:** воронка и админка — lazy-роуты, recharts только в чанке админки. Шрифты self-hosted (никаких внешних CDN).

## Языки (RU по умолчанию, EN)

```
packages/shared/src/i18n.ts            collectMessages, localizeFunnel/localizeResult, unitFor, catalogFor
configs/translations/*.json            каталоги: { funnelId, locale, messages: { "<исходный текст>": перевод } }
apps/server/src/services/translations  загрузка и zod-проверка каталогов при старте
apps/web/src/lib/language.ts           выбранный язык: ?lang= → localStorage → ru
apps/web/src/funnel/i18n, admin/i18n   словари интерфейса (кнопки, подписи) ru/en
```

- **Контент — данные, интерфейс — код.** Тексты воронки живут в конфиге, поэтому и переводы — данные рядом с конфигом, а не строки в React. Кнопки и подписи («Продолжить», «Шаг 3 из 6», вся админка) — словари в коде: они не зависят от воронки.
- **Ключ перевода — исходный текст (схема gettext).** Выданные конфиги менять нельзя и в них нет ключей; исходная фраза стабильна между версиями, поэтому один каталог обслуживает v1, v3 и будущие версии. Нет перевода — показывается исходный текст: новая версия никогда не ломается, только частично остаётся на английском. Тест покрытия перечисляет все пользовательские строки обоих конфигов и падает, если какой-то нет в русском каталоге.
- **Единицы — формы `Intl.PluralRules`** (`1 человек / 3 человека / 5 человек`). Каталог исходного языка допустим как слой поправок: `en.json` задаёт только `person/people`, потому что в конфиге единица дана одной формой.
- **Язык — только отображение.** Сессия получает каталоги своей воронки вместе с закреплённой версией; клиент переводит на лету. Язык не уходит на сервер и не участвует в закреплении версии, назначении варианта, событиях и аналитике, поэтому смена языка посреди воронки — просто перерисовка без новой сессии и без событий. Контроллер воронки работает с непереведённым конфигом: id, ответы и навигация от языка не зависят.
- **Русский по умолчанию** (`DEFAULT_LANGUAGE`), выбор запоминается в браузере; один выбор на всё приложение — воронку и админку. Админка переводит видимый контент конфигов (названия шагов, результатов, release note) тем же каталогом.
- **Технические данные не переводятся:** id шагов, имена событий, коды ошибок API, логи, CLI.

## Тесты

- `packages/shared/test` — движок: условия, навигация, валидация, результат, хэш варианта, diff, локализация и покрытие русского каталога.
- `apps/server/test` — реальный HTTP через `app.inject` на in-memory SQLite: закрепление версии, стабильность A/B, дедупликация, публикация/откат, аналитика с ручным расчётом, апгрейд миграций; `iteration2.test.ts` — вторая итерация целиком.
- `apps/web/test` — очередь, контроллер, storage, poller, выбор языка и форматирование чисел в node с фейками браузера.

Каждое требование проверяется на том уровне, где реализовано; вся сюита ~2 с, без браузера и сети.

## Инфраструктура

- **TypeScript strict** (+ `noUncheckedIndexedAccess`, `verbatimModuleSyntax`), **ESLint** flat config (typescript-eslint, react-hooks, react-refresh, 0 предупреждений), **Prettier**, `.editorconfig`.
- **CI** (GitHub Actions, Node 22 как в проде): `npm ci → format:check → lint → typecheck → test → build`.
- **Dockerfile** двухстадийный: сборка → `npm prune --omit=dev`. Фронтовые пакеты — devDependencies (живут только в vite-бандле), поэтому в образе остаются fastify, zod, better-sqlite3. HEALTHCHECK на `/api/health`. Без `VOLUME` (Railway запрещает) и под root (Railway монтирует volume root-owned).
- **railway.json:** 1 реплика (SQLite на одном volume), healthcheck, рестарт при падении.
- **`.env.example`** — единый список переменных; `.env` читается через `node --env-file-if-exists`, без dotenv.

## Осознанные ограничения

Один инстанс (SQLite на volume — горизонтального масштабирования нет). Без внешних ключей — целостность проверяется в сервисах. Дашборд и список версий открыты для чтения без токена (в них нет id сессий и ответов), всё остальное — по токену.
