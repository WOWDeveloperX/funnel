# Funnel Runtime

Мини-платформа для многошаговых веб-воронок. Фронтенд рендерит воронку по JSON-конфигу с бэкенда, без захардкоженных экранов. Конфиги версионируются: публикация и откат проходят без передеплоя. Внутри версии идёт A/B-эксперимент. События собираются собственным идемпотентным эндпоинтом. Дашборд считает метрики по уникальным сессиям.

Стек: TypeScript-монорепо (npm workspaces) · React 19 + Vite + Tailwind v4 · Fastify 5 + SQLite (better-sqlite3) · общий движок `@funnel/shared` · zod · Vitest.

## Ссылки

- Публичная воронка: добавляется после деплоя.
- Админка: `/admin` на том же домене (версии), а также `/admin/analytics`, `/admin/events`, `/admin/sessions`.
- Репозиторий: добавляется после публикации на GitHub.

Админ-токен передаётся отдельно, в репозитории его нет.

## Быстрый старт

Нужен Node.js ≥ 22 (версия в `.nvmrc`).

```bash
npm ci
cp .env.example .env   # необязательно: все переменные имеют значения по умолчанию
npm run dev            # API :3000 (tsx watch) + Vite :5173 с прокси /api
```

- Воронка: http://localhost:5173/
- Админка: http://localhost:5173/admin

При первом запуске применяются миграции. Если база пустая, публикуется и активируется `configs/funnel-v1.json`.

```bash
npm run generate       # 150 синтетических сессий через HTTP API с самопроверкой дашборда
npm test               # все тесты
npm run build && npm start   # prod-сборка: API и SPA на одном порту, http://localhost:3000
```

Полезные URL воронки:

- `/?variant=B&reset=1`: новая сессия с принудительным вариантом B (override).
- `/?utm_source=facebook&utm_medium=paid_social&utm_campaign=meta_spring`: UTM записываются в сессию.
- `?reset=1`: забыть текущую сессию и начать новую.

## Скрипты

- `npm run dev`: сервер и Vite в watch-режиме.
- `npm run build` / `npm start`: сборка (`apps/web/dist`, `apps/server/dist/server.js`) / запуск prod-сборки.
- `npm test` / `npm run test:watch`: Vitest по всем пакетам.
- `npm run typecheck`: `tsc --noEmit` для shared, server, web и scripts.
- `npm run lint` / `npm run lint:fix`: ESLint (0 предупреждений).
- `npm run format` / `npm run format:check`: Prettier.
- `npm run generate -- [--sessions 150] [--url …] [--seed 42] [--no-utm-rate 0.1]`: генератор трафика, все флаги в `--help`.
- `npm run publish-config -- <config.json>`: валидация, diff с активной версией и публикация; также `--validate-only`, `--activate-only <v>`, `--rollback`.

Скрипты работают через тот же HTTP API, что и браузер. URL берётся из `--url` или `$FUNNEL_URL`, токен из `--token` или `$ADMIN_TOKEN`.

Генератор создаёт сессии с разными UTM (`meta_spring`, `google_brand`, `newsletter_oct` и ~10 % без UTM) и с вариантами A и B (~8 % через override). Проходы идут по реальным веткам движком `@funnel/shared`, отвал у A и B разный, есть возвраты назад. События уходят перемешанными пачками: внутри пачек есть дубли, часть пачек отправляется повторно целиком, у части сессий «прыгают» клиентские часы, плюс три заведомо битых события. В конце скрипт сверяет свою «истину» с приростом `GET /api/admin/analytics` и ответами ingest. При любом расхождении он печатает ✗ и завершается с кодом 1.

## Переменные окружения

Все переменные перечислены в `.env.example`. `npm run dev`, `npm start` и CLI читают `.env`, если файл есть.

- `PORT` / `HOST` (по умолчанию `3000` / `0.0.0.0`): адрес HTTP-сервера.
- `DATABASE_PATH` (по умолчанию `./data/funnel.db`): файл SQLite; относительный путь считается от корня репозитория.
- `ADMIN_TOKEN` (по умолчанию не задан): защищает `POST /api/admin/*`, `GET /api/admin/sessions` и `GET /api/admin/events`; **обязателен в продакшене**.
- `SEED_CONFIG` (по умолчанию `configs/funnel-v1.json`): конфиг для пустой базы.
- `TRANSLATIONS_DIR` (по умолчанию `configs/translations`): каталоги переводов контента воронки, см. «Языки».
- `WEB_DIST` (по умолчанию `apps/web/dist`): собранный SPA, который раздаёт сервер.
- `LOG_LEVEL` (по умолчанию `info`): уровень логов pino.
- `API_PORT` (по умолчанию `3000`): порт API и цель прокси Vite, только для `npm run dev`.
- `FUNNEL_URL` (по умолчанию `http://localhost:3000`): адрес сервера для `generate` и `publish-config`.

При неверных значениях сервер не стартует и называет в ошибке каждую неверную переменную.

## Архитектура (кратко)

```
packages/shared   единый движок: схема конфига, validateConfig, условия, навигация, прогресс,
                  валидация ответов, расчёт результата, whitelist событий, хэш варианта, типы API;
                  работает в браузере, на сервере, в генераторе и тестах
apps/server       config → app → routes → services → SQLite; SQL только в services
apps/web/funnel   FunnelController (сессия, навигация, сохранение) + очередь событий в localStorage
apps/web/admin    версии, аналитика, живой лог событий, сессии
scripts           generate (трафик) и publish (публикация без передеплоя)
configs           funnel-v1.json, funnel-v3.json: выданы с заданием и не изменяются
configs/translations  переводы контента воронок: <funnelId>.<lang>.json
```

Почему код устроен именно так — в [ARCHITECTURE.md](ARCHITECTURE.md).

Тексты внутри `configs/*.json`, включая «For this demo…», взяты из выданных конфигов как есть. Пользователь видит их в переводе из `configs/translations` (см. «Языки»).

## Языки

Интерфейс двуязычный: **русский по умолчанию** и английский. Язык выбирается переключателем RU | EN в воронке и в админке или параметром `?lang=ru|en` и запоминается в браузере. Смена языка посреди воронки не создаёт новую сессию и не отправляет событий: язык влияет только на отображение и не участвует в закреплении версии, назначении варианта, событиях и аналитике.

- **Интерфейс** (кнопки, подписи, ошибки, админка) переведён в коде веб-приложения.
- **Контент воронки** — данные, а не код. Конфиги написаны на английском (`locale: en-AU`) и не меняются, а переводы лежат рядом: `configs/translations/<funnelId>.<lang>.json`, формат `{ funnelId, locale, messages }`. Ключ сообщения — исходный английский текст из конфига, поэтому один каталог обслуживает все версии воронки: совпадающие строки v1 и v3 переводятся один раз.
- **Метка результата.** Если у результата нет `badge`, экран результата показывает его id с пробелами вместо `_` (`async native`). Эта строка входит в `collectMessages` и переводится в каталоге, как остальной контент.
- **Единицы измерения** записываются формами множественного числа по категориям `Intl.PluralRules`: `"days": { "one": "день", "few": "дня", "many": "дней", "other": "дня" }`.
- **Каталог исходного языка** допустим как слой поправок: `workstyle-planner.en.json` задаёт только английские формы единиц (`1 person`, `3 people`), потому что в конфиге единица дана одной формой.
- **Фолбэк.** Если строки нет в каталоге, показывается исходный текст. Новая версия с непереведённым текстом не ломается, а частично показывается на английском.
- **Технические данные** не переводятся: id шагов и результатов, имена событий, коды ошибок API, логи, вывод CLI.

Каталоги загружаются и проверяются при старте сервера: при битом файле сервер не стартует и называет файл в ошибке. Сессия получает каталоги своей воронки в `SessionState.translations`, админка — через `GET /api/funnels/:funnelId/translations`.

**Как перевести новую версию.** Опубликовать конфиг как обычно, затем добавить в `configs/translations/<funnelId>.ru.json` переводы новых строк. Тест `packages/shared/test/translations-coverage.test.ts` перечисляет непереведённые строки выданных конфигов. Переводы применяются после перезапуска сервера, конфиг перепубликовывать не нужно.

**Как добавить язык.** Положить каталог `configs/translations/<funnelId>.<lang>.json` с переводами всех строк (их список возвращает `collectMessages(config)` из `@funnel/shared`), добавить код языка в `SUPPORTED_LANGUAGES` (`packages/shared/src/i18n.ts`) и словарь интерфейса в веб-приложении.

## Модель данных

SQLite в режиме WAL. Миграции хранятся упорядоченным append-only массивом в `apps/server/src/db.ts`, применённые версии записываются в `schema_migrations`. При старте применяются недостающие миграции, в том числе к уже существующей базе. Для второй итерации схему менять не понадобилось: новые шаги, события и результаты являются данными.

- `funnel_versions(funnel_id, version, config_json, config_hash, …)`: неизменяемые версии конфигов, `config_hash` считается как sha256 канонического JSON.
- `version_activations(id, funnel_id, version, previous_version, action, created_at)`: журнал `seed / publish / activate / rollback`; откат работает как стек.
- `active_versions(funnel_id PK, version, activated_at)`: указатель на активную версию.
- `sessions(id PK, funnel_version, experiment_id, variant, variant_source, utm_*, answers_json, current_step_id, result_id, expires_at, …)`: сессия закреплена за версией, вариантом и UTM; **сырые ответы хранятся только здесь**.
- `events(event_id PK, session_id, name, step_id, funnel_version, variant, utm_*, client_ts, server_ts, properties_json, batch_id)`: принятые события.
- `duplicate_deliveries(event_id, batch_id, received_at)`: каждая повторная доставка уже сохранённого события, для живого лога.
- `rejected_events(event_id, batch_id, reason, payload_json, received_at)`: отклонённые события с причиной; у свойств сохраняются только ключи.
- `ingest_batches(id, total, accepted, duplicates, rejected, received_at)`: статистика по пачкам.

Внешних ключей в схеме нет. Связи проверяются в сервисах: например, событие с неизвестной сессией отклоняется как `unknown_session`.

## HTTP API

- `POST /api/sessions` (открыт): `{funnelId?, query}` → `201` SessionState: версия, вариант, UTM и конфиг, уже разрешённый для варианта.
- `GET /api/sessions/:id` (открыт): `200` / `404 not_found` / `410 expired`.
- `PUT /api/sessions/:id/state` (открыт): `{answers, currentStepId}`, побеждает последняя запись.
- `POST /api/sessions/:id/result` (открыт): сервер проверяет ответы и считает результат → `{resultId, result}` / `400 invalid_answers`.
- `POST /api/events` (открыт): пачка `{events: [1..500]}` → `{batchId, accepted, duplicates, rejected[]}`.
- `GET /api/funnels/:funnelId/translations` (открыт): `{funnelId, catalogs}`, каталоги переводов воронки (пустой список, если их нет) / `404 not_found` для неизвестной воронки.
- `GET /api/health` (открыт): `{ok, activeVersion, db, adminAuthRequired}`.
- `GET /api/admin/versions`, `/versions/:v` (открыт): список версий с журналом и конфиг конкретной версии.
- `GET /api/admin/analytics` (открыт): агрегаты для дашборда.
- `POST /api/admin/versions/validate` (токен): валидация, сводка и diff с активной версией.
- `POST /api/admin/versions` (токен): `201` новая версия · `200` идентичная (активируется) · `409` тот же номер с другим содержимым · `422` невалидный конфиг.
- `POST /api/admin/versions/:v/activate`, `/rollback` (токен): активировать версию / откатиться на предыдущую в стеке.
- `GET /api/admin/events`, `/sessions` (токен): живой лог доставок и список сессий.

Токен передаётся в заголовке `x-admin-token`. Списки событий и сессий закрыты, потому что содержат id сессий, а по id сессии читаются её ответы. Авторизация привязана к Fastify-scope совпавшего маршрута, поэтому `/api/%61dmin/…` её не обходит.

## События

| Событие                   | Отправитель                                      | `step_id` | `properties`                                        |
| ------------------------- | ------------------------------------------------ | --------- | --------------------------------------------------- |
| `session_started`         | **сервер**, в транзакции создания сессии         | `null`    | —                                                   |
| `step_viewed`             | клиент, при каждом показе шага                   | шаг       | `step_type, visible_step_index, visible_step_count` |
| `answer_submitted`        | клиент, при переходе вперёд с валидным ответом   | шаг       | `answer_kind` (тип шага, без значения)              |
| `step_completed`          | клиент, при переходе вперёд                      | шаг       | `next_step_id`                                      |
| `back_clicked`            | клиент, кнопка Back и браузерный back            | текущий   | `destination_step_id`                               |
| `result_viewed`           | клиент, при показе результата                    | result    | `result_id`                                         |
| `cta_clicked`             | клиент                                           | result    | `result_id, action`                                 |
| `recommendation_expanded` | клиент, только в версиях, где оно разрешено (v3) | result    | `result_id, action, source`                         |

Каждое сохранённое событие содержит `event_id`, `session_id`, `server_ts` и `client_ts`, `funnel_id`, `funnel_version`, `experiment_id`, `variant`, `step_id`, `utm_source / utm_medium / utm_campaign` и `properties`.

- **Повтор `event_id` не создаёт дубль**: `event_id` — первичный ключ, вставка через `INSERT … ON CONFLICT DO NOTHING`; повтор попадает в `duplicates`, в том числе внутри одной пачки.
- **Приём пачкой**: до 500 событий, вся пачка обрабатывается в одной транзакции.
- **Повтор после timeout безопасен**: клиент повторяет пачку с теми же id и убирает событие из очереди только после того, как сервер вернул его в `accepted ∪ duplicates ∪ rejected`.
- **Битое событие не ломает пачку**: события проверяются по одному; при ошибке пишется `rejected_events` с причиной (`invalid_shape`, `unknown_session`, `server_only_event`, `event_not_allowed_for_version`, `unknown_step`, `missing_step_id`, `step_mismatch`, `invalid_timestamp`), остальные принимаются.
- **Версия, вариант и UTM**: всегда копируются из строки сессии, поля из тела события игнорируются.
- **Набор событий зависит от версии**: событие проверяется по `events.allowed` **закреплённой** версии, поэтому v1-сессия не может прислать `recommendation_expanded`.
- **Сырые ответы не попадают в аналитику**: ответы хранятся только в `sessions.answers_json`; `properties` фильтруются по whitelist версии, допускаются только примитивы, строки обрезаются до 256 символов.

Клиентская очередь лежит в `localStorage` и переживает перезагрузку. Она отправляет события раз в 1,5 с или при накоплении 10, при сетевых ошибках и 5xx повторяет с экспоненциальным backoff, а при скрытии вкладки отправляет очередь через `sendBeacon`.

## Правила агрегации

Единица счёта — **уникальная сессия**, а не событие. В когорту попадают сессии, подходящие под фильтры: версия, вариант, `utm_campaign` и исключение override. Факты каждой сессии считаются по позициям шагов в **её собственной** последовательности (версия + вариант), а не по порядку прихода событий.

- **started**: все сессии когорты. У каждой есть серверный `session_started`.
- **viewed(S)**: у сессии есть любое шаговое событие с `step_id = S`. Если безусловный шаг пройден, а `step_viewed` потерялся, просмотр всё равно засчитывается.
- **progressed(S)**: шаг просмотрен и есть `step_completed(S)` или событие на более поздней позиции. **dropOff = viewed − progressed**, конверсия равна `progressed / viewed`.
- **Условные шаги**: `eligible` — сессии, в последовательности которых шаг есть; `shownRate = viewed / arrived`. Поэтому `office_days` не выглядит отвалом, а `tool_count`, которого нет у B в v3, считается только от сессий v3-A.
- **reachedResult**: есть `result_viewed` или `cta_clicked` и при этом серверный результат (`sessions.result_id`).
- **CTR**: `ctrFromStarted = ctaClicked / started` (основная метрика) и `ctrFromResult = ctaClicked / reachedResult`.
- **Повторные просмотры, возвраты назад, дубли**: каждый факт считается один раз на сессию. Повторы видны отдельно как `avgViewsPerSession` и `backFrom`, дубли отсекаются ещё на ingest.
- **События не по порядку**: на результат не влияют, потому что факты выводятся из множества событий сессии, а не из их последовательности. Сессии с перепутанными `client_ts` считаются в `dataQuality.outOfOrderSessions`.
- **Сравнения**: варианты сравниваются по `step_id`, а не по позиции шага. Блок вариантов игнорирует фильтр варианта, блок версий игнорирует фильтр версии.
- **UTM**: фильтр по одной или нескольким кампаниям; `(none)` означает сессии без `utm_campaign`.
- **Качество данных**: `duplicatesDropped`, `rejected`, `outOfOrderSessions`, `unverifiedResultSessions`.

Те же правила показаны на дашборде в поповере «Как считается».

## A/B-эксперимент

**Гипотеза.** Вариант B начинается с самых простых и «личных» вопросов (формат работы, часовые пояса), а intro и результат формулирует через проблему и конкретную выгоду. Так у B должно быть меньше отвала на первых шагах и больше кликов на CTA.

**Основная метрика:** `ctrFromStarted`, то есть доля начавших сессий, кликнувших основной CTA. Она сквозная: учитывает и доходимость, и привлекательность результата. Вспомогательные метрики: completion rate, CTR от увидевших результат, отвал по шагам. **Guardrail:** медианное время до результата не должно расти.

- Вариант назначается **на сервере** при создании сессии: `fnv1a32(experimentId:sessionId) % sumWeights` по весам вариантов. Назначение сохраняется в сессии и не меняется после refresh.
- Override `?variant=A|B` работает только при создании сессии и помечается `variant_source = 'override'`. Такие сессии в A/B-тест не входят: принудительно выбранный вариант не является случайным назначением.
- Вариант меняет тексты (`stepOverrides`), порядок и набор шагов (`stepSequence`) и экран результата (`resultOverrides`).
- Оценка: двухпропорционный z-тест по `ctrFromStarted` **внутри одной версии**. v1 и v3 проверяют разные изменения, поэтому не смешиваются. Разница значима при p < 0,05, данных достаточно при n ≥ 30 в каждой группе.

## Вторая итерация (v1 → v3)

`configs/funnel-v3.json` добавляет условную ветку `security_constraints` (появляется при выборе `compliance` в `priorities`) и шаг `meeting_hours`, убирает `tool_count` у варианта B, вводит новые результаты и новое событие `recommendation_expanded`.

Публикация и откат:

- через админку: `/admin` → «Опубликовать новую версию» → вставить `configs/funnel-v3.json` → проверить чек-лист и diff → «Опубликовать». Откат — кнопкой «Откатить на v1»;
- через CLI: `npm run publish-config -- configs/funnel-v3.json` и `npm run publish-config -- --rollback`.

Старые сессии доходят до конца на v1 по правилам v1, новые стартуют на v3. После отката новые сессии снова идут на v1, а начатые v3-сессии продолжают на v3. Схему базы менять не нужно, аналитика хранит обе версии раздельно. Весь сценарий автоматически проверяет `apps/server/test/iteration2.test.ts`.

## Агентский процесс

- Работа разбита по владению файлами: shared, server, analytics, web-funnel, web-admin, scripts, tooling. Агенты работают параллельно и не пересекаются в файлах.

- Каждое исправление проверяется тестами, typecheck, генератором и E2E на prod-сборке.
- Итоговая ответственность и понимание кода остаются за автором: решения и компромиссы описаны в этом README.

## Деплой (Railway)

`Dockerfile` двухстадийный, на Node 22: `npm ci` → `npm run build` → `npm prune --omit=dev`, плюс HEALTHCHECK. `railway.json` задаёт builder Dockerfile, 1 реплику и healthcheck `/api/health`.

1. New Project → Deploy from GitHub repo.
2. Подключить Volume в `/data`. `DATABASE_PATH=/data/funnel.db` уже задан в образе.
3. Variables: `ADMIN_TOKEN` (длинное случайное значение), при необходимости `LOG_LEVEL`. `PORT` Railway задаёт сам.
4. Settings → Networking → Generate Domain.

Новые версии конфига публикуются без передеплоя через `/admin` или `publish-config --url https://<домен> --token …`.

## Ограничения и допущения

- **Один инстанс.** SQLite и Volume на Railway рассчитаны на одну реплику. Горизонтальное масштабирование требует другой БД.
- **Один общий `ADMIN_TOKEN`** без пользователей. Журнал версий фиксирует, что и когда изменилось, но не кто это сделал.
- **`session_started` создаёт сервер**, поэтому у этого события нет `client_ts`. Такое же событие от клиента отклоняется.
- **Сырые ответы хранятся только в `sessions.answers_json`.** Ответы из скрытых веток не удаляются, но не участвуют в расчёте видимости и результата.
- **Откат работает как стек.** Повторный откат уходит глубже по истории активаций; если откатываться некуда, сервер возвращает `409`.
- **Guardrail по времени** считается по часам клиента. Если часы сбиты и интервал получается отрицательным, он засчитывается как 0.
- **UTM:** сохраняются только `utm_source`, `utm_medium` и `utm_campaign`; `utm_term` и `utm_content` отбрасываются.
- **`duplicatesDropped` и `rejected`** — глобальные счётчики ingest, фильтры дашборда на них не действуют: у отклонённого события может не быть валидной сессии.
- **План за CTA.** CTA раскрывает `result.plan` из конфига. В выданных конфигах плана нет, поэтому показывается общий план внедрения на 4 недели. Это единственный содержательный текст вне конфига.
- **Предпросмотр неактивной версии** не реализован: новая сессия всегда стартует на активной версии.
- **Язык.** Русский и английский; контент воронки переводится каталогами из `configs/translations`, см. «Языки». Каталоги читаются при старте, поэтому новый перевод требует перезапуска сервера (в отличие от публикации конфига).
